# Spec v1.5 to v1.6: what changed and what it means for the PoC

Written on 25 Nov 2026 by comparing `spec-v1.5.md` with `spec-v1.6.md` line by line and checking the code. A later session reads this instead of repeating the comparison.

The file `spec-v1.5.md` holds the older text: it still says "quality gate", "hygiene" and "confidence". The header of v1.6 credits some of the changes below to Version 1.5. For the PoC the only question is what differs between the two files, and that is this list.

## What the complexity change touches (for the F16 deep dive)

- Prompt and schema: `backend/src/main/resources/judgment/prompts/feature-work-complexity-v1.md` and `.../schemas/feature-work-complexity-v1.json`. A released prompt is never edited (decision 129); the change is `feature-work-complexity/v2`. `PromptLibraryTest` pins the file hashes. The version string is in `judgment/FeatureWorkJudge.java`.
- Input (`judgment/FeatureWorkInput.java`): work item texts and a short form of each PR digest. No code, no file list, nothing about the rest of the repository. The digest's reason and facts are stored but not passed on; a depth is hard to judge without them.
- Storage: the whole answer goes into `judgment.value` (jsonb). A list of problems with depths fits there without a migration. `judgment.facts` is fixed to fact and link and is the wrong place.
- Readers of the complexity: `scoring/ScoredItems.java` and `analytics/WorkComplexity.java` read `value ->> 'complexity'`. If the key and its four values stay, they do not change. The tier still comes from the setting `evidence.complexity_tiers`.
- Judging again: the prompt version is part of the input hash, so with v2 every Feature work item is judged again and the new row supersedes the old one. Scoring, analytics and the web read the current row.
- Exchange mode: `.claude/skills/judge/SKILL.md` names `feature-work-complexity/v1` in its stage table, and tells the subagents to read nothing but the request.
- Web: `web/app/items/[itemId]/JudgmentView.tsx` shows tier, complexity, reason and facts. The API already sends the full `value`, so the problems and depths need only the page.

## Not covered by the PoC after this change

- The search of the repository for an earlier solved example (rule "the first solution gets the credit"). The AI judges from the tickets and digests and marks each problem "earlier example not checked" (decision 303).
- The growing set of lead-confirmed examples. The PoC uses the five examples of spec 6.2 as they are (decision 306).
- Correcting one depth by a lead (no correction screen, decision 3).
