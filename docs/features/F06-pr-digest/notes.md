# F06 JudgmentModel, Stage 1 PR digest, and the builders that need the PR work type: notes

## Batch 1: built for later tasks

Code that nothing calls yet; the `pull-request-digest` job (task 8) uses it.
- `ProviderChain.startRun()`, `providerNames()`, `callsPerProvider()`: the job resets the limits at its start, fails when there is no provider, and writes `calls_<name>`.
- `JudgmentStore.hasModelJudgment(kind, inputHash)`: the skip-on-same-input check before a call.
- `JudgmentStore.write` supersedes the current judgment of the same subject. A new PR record version is a new subject, so the job (task 8) must supersede the digest of the older version of the same PR itself; `NewJudgment` now carries an explicit `supersedesId` (task 8), which the job sets from `JudgmentStore.findCurrentOfPullRequest`.
- The client sends no `temperature` (design 2 names it, plan task 4 does not list it as a property); add it if a prompt needs it.

## Differences from the plan

- Batch 1: extra classes `JudgmentProvider`, `CallPolicy`, `JudgmentSubject`, `JudgedBy` (the client needed the provider shape before task 4's properties). The provider error text is cut at `ei.judgment.max-error-characters`, a property, because `judgment` holds no number constant (decision 53). `judgment.confidence` is not mapped on the entity: F06 never reads it; F07 maps it. `NewJudgment` has one constructor and no factory.
- Task 6: the docs group that orders patches (`docs/`, `*.md`, `*.adoc`, `*.rdoc`, `*.txt`) is a constant in `DiffFileFilter`, not a setting: it only decides which patches are dropped first when the budget is short and decides no evidence; the test group reads `evidence.test_paths`. A patch that does not fit is left out and the next, smaller ones are still tried. A file GitHub gave no patch for (binary or very large) is named, and does not set `judgedOnPartialCode`; the `truncated` flag of the diff record is not read.
- Task 7: extra class `InvalidDigestException` (the answer check needs an exception the job can retry on) and a test `DigestFactsTest`. The yes/no fields of the digest are JSON booleans. `workTypeTier` is an object `{tier, reason}` with `tier` one of T1, T2, T3, not_applicable (the strict schema allows no null); an answer with work type refactor, performance, security or infra and no tier is refused. A fact with a changed file links to `<PR url>/files` (no per-file anchor, as the design says) and its text carries the path in brackets; a path not in the PR keeps the PR link. The yes/no, enum and text values of the answer are checked; extra fields are ignored. `PromptLibraryTest` pins the SHA-256 of the prompt and of the schema file.
- Task 8: extra classes `PullRequestDigester` (the work on one pull request, so the job only loops, counts and fails at the end), `WaitMeter` (a `Sleeper` that adds up the waits; `ProviderChain` takes it and reports `waited()`, reset by `startRun()`), and `JudgmentStore.findCurrentOfPullRequest`. `rate_limit_wait_seconds` is every wait of the model clients, so it includes the short waits before a retry after a 5xx. "One PR per transaction" is the store's own transaction around the one judgment row; the model call is made outside any transaction, so no database connection is held while it waits. `GitHubImportArguments.pullRequestNumbers` is now public so the job reads `pullRequestNumbers` with the same rule. A listed number with no stored pull request fails the run at its end, named `#<number> (not stored)`. The job fails at its start with `LLM_PROVIDER_1_API_KEY` named when no provider has a key. The model call counts `model_calls` and the tokens count every answered call, a refused answer included.
- Task 9: `ItemFields` gets no new method here; each builder adds the field shape it uses in its own task, so no method waits unused. `PullRequestDigests.currentOf` returns a `CurrentDigest(judgment, digest)` so the tier judgment can copy reason, facts with links, model and prompt version from the row. `EvidenceItemResponse` (api) had to cover the five new types to compile: they show their `pullRequest` as title and link; task 13 adds the tier.
- Task 10: `LinkedPullRequests` now reads every PR of a human, with the links it has (none, or only `not_visible` ones, gives an empty `workItems`) and its current digest (`LinkedPullRequest.digest`); F05's builders loop over `workItems`, so a PR with none still gives them nothing. `Read` counts `pullRequestsWithoutDigest` for the job (task 12). `PathPatterns` moved from `judgment` to `common` and is public, because `evidence` needs the same `evidence.test_paths` rule as the diff filter. `BuiltItem` carries `digests` (empty for F05); the content hash adds `digestJudgmentIds` only when there are some, so F05's stored hashes are unchanged. Extra classes `ItemSources` (the sources of an item of one PR) and the test helper `StoredDigestsFixture`.
- Task 11: a PR whose non-Bug links include one under a Feature, or that links only Bugs, gives nothing from the work type; a PR with a Bug link and a standalone non-Bug link is judged by the non-Bug links (decision 141). A PR that links two standalone items feeds the Feature work group of each (decision 149). The Feature work of a standalone item groups only the author's PRs on it whose digest says feature or enhancement; a PR on it with another work type gives that work type's item. Its sources hold the PR and diff records of every member PR and the work item record. A failed or missing diff record fails the item by its key, as a missing person does.
- Task 12: `EvidenceItemStore` is unchanged: `ItemTiers` finds the new row through `EvidenceItemRepository.findCurrentByKey`. The job tries the tier of every built Test change, Refactor, Security and Infra item, changed or not, and `ItemTiers` writes only when the current row has no `item_tier` judgment, so a tier a failed run did not write is written by the next run and an unchanged item gets none. The input hash covers the kind, the digest id, the item row id and the item's content hash (the row id is in it so an item that returns to an earlier content still gets its tier). The tier judgment is `judged_by` model with the digest's model and prompt version: no call is made. A tier that cannot be written fails the run naming `<key> (tier)`; the item stays. New counts: `pull_requests_without_digest`, `item_tiers_written`.
- Task 13: the plan listed no new class, but the `api` package needed a public reader of the current tier: `judgment.CurrentItemTiers` (one query for all item rows of a developer, new `JudgmentRepository.findCurrentOfEvidenceItems`) and the record `ItemTier(tier, reason)`. `EvidenceItemResponse.tier` is `{tier, reason}` or null; `TypeCounts` has the five new counts (`testChange`, `refactorPerformance`, `security`, `infraRelease`, `documentation`).
- Task 14: the web has `app/developers/evidenceSections.ts` (the order, titles and colours of the eight types, used by the count badges and the page) and the section component `PullRequestItemSection` (title, tier badge T1/T2/T3, reason, links; no badge when the item has no tier, as Documentation never has one). Colours: Test change cyan, Refactor and performance amber, Security red, Infra and release pink, Documentation slate; tier badges are three blues. A Feature work or Bug fix item of a PR without a work item (`fields.noWorkItem`, no `feature`/`bug`) made `EvidenceItemResponse` throw; it now takes the title of its first pull request and shows only pull request links (test `featureWorkAndBugFixWithoutAWorkItemShowTheirPullRequest`, committed with task 14 because it was found there).

## Follow-ups

- `OpenAiCompatibleClient`: `temperature` is not sent (design "Main flows" 2 names it). No number depends on it; add it with a property if the 50-PR run shows unstable answers.
- `WorkTypeItemBuilder.java:121`: a Documentation item's `files` lists every changed file, code included; spec 6.5 means the documentation files.
- `WorkTypeItemBuilder`: a Bug fix with no work item can hold `work_package` sources (a standalone link) while its fields say `noWorkItem: true` and list none.
- `ProviderLimitReachedException.providerName()` is used only by a test.
- `JudgmentModelBoundaryTest`: its client-package list does not include Spring's `RestClient` (decision 156), so the "only a JudgmentModel uses a model client" rule checks nothing for this client. A rule on `RestClient` inside `judgment` would.
- `PullRequestDigests.CurrentDigest` exposes the `Judgment` entity to `evidence`; expose only the fields `ItemTiers` copies.
- `DigestInput` names a file twice under "Patches not sent" when it is both excluded and has no patch.
- `PullRequestDigester.bodyOf` reads the payload directly instead of through `PullRequestFacts`.
- `JudgmentStore` javadoc cites decision 127 for the skip rule; it is 157.
- Web: the "no work item" mark of Feature work and Bug fix items is not shown.
- The diff record's `truncated` flag is not read (false on all 215 stored diffs, 22 Nov 2026); a truncated diff should set `judgedOnPartialCode`.
- A malformed `x-ratelimit-*` header is not tested; the client then does not pace.

## What a later feature should know

- Order of jobs: `github-import`, `openproject-import`, `identity-build`, `pull-request-digest`, `evidence-build`. `pull-request-digest` needs a provider key in `.env`; with all providers at their limit it stops, counts `pull_requests_left_for_later` and succeeds; run it again later.
- F07 reads digests through `judgment.PullRequestDigests.currentOf(prExternalId)` and calls the model through `JudgmentModel` (the `ProviderChain` bean). Add a prompt as a new versioned file under `resources/judgment/prompts/` and pin its hash in `PromptLibraryTest`; add new kinds to the `judgment.kind` check in a new migration.
- The input hash does not include the model (decision 157): a digest is not redone when another provider answers. To judge again, add a prompt version.
- Tiers of items are `item_tier` judgments on the item row; `judgment.CurrentItemTiers.ofItems(ids)` reads them in one query.
- `ei.judgment.max-diff-characters` (12,000) and `min-remaining-tokens` (6,000) are sized for Groq's free 8,000 tokens per minute.
